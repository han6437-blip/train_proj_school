# Agent 开发面试官：20 题可直接口述版

这份回答围绕企业售后智能客服与上门预约 Agent 项目整理。口述时建议先说结论，再结合一次具体请求说明实现，最后补充异常处理和技术取舍。每题控制在 1～3 分钟即可。

## 1. 请用 3 分钟介绍项目，并讲清一次完整请求链路

我做的是一个企业售后智能客服与上门预约 Agent 系统，主要解决产品咨询、故障排查、工程师匹配和预约过程中信息反复收集、跨系统操作容易出错的问题。我负责的核心闭环包括意图路由、会话恢复、人工确认、预约幂等与事务；完整架构再把混合 RAG、结构化槽位模型和异步通知串进同一条业务链路。

系统采用“确定性 Router + Supervisor + 专业 Agent”的混合架构。简单咨询直接进入咨询 Agent，简单预约直接进入预约 Agent；只有跨领域、多步骤请求才进入 Supervisor。咨询 Agent 负责基于知识库回答，预约 Agent 负责收集槽位和组织确认，用户行为分析 Agent 异步处理已完成事件。模型只负责理解、规划和提出工具调用，权限、状态机、幂等、冲突检查和数据库事务都由业务代码决定。

例如用户说：“空调报 E3，帮我预约明天下午维修。”API 入口先完成认证、租户隔离、输入校验，并生成 Trace ID。Router 识别出这是咨询加预约的复合任务，交给 Supervisor。Supervisor 先调用咨询 Agent，经过元数据过滤、BM25 与 Dense 双路召回、RRF 融合和 Cross-Encoder 精排，生成带来源的排查建议。

随后预约 Agent 把用户原话、已有槽位和固定 Schema 交给本地 Qwen3-1.7B，以 Non-Thinking 模式输出结构化结果，例如设备、故障码、原始日期表达、时间段和缺失字段。“明天下午”的具体日期由确定性时间服务结合请求时间和用户时区解析，模型不直接做日期运算。缺少地址或联系人时，工作流保存状态并定向澄清。

信息齐全后，服务查询具备对应技能且时段可用的工程师，返回带版本的候选方案。用户明确确认后，预约 Service 会再次校验身份、租户、确认内容、幂等键和最新排班，并在一个事务里写入预约记录、幂等结果和 Outbox 事件。最终 Supervisor 汇总故障建议和预约结果，通知与用户行为分析异步消费事件。调试阶段用统一关联 ID 和结构化事件串联各节点；跨服务部署时用同一 Trace Context 串联模型、检索、工具和数据库 Span。

## 2. 为什么拆成多个专业 Agent，而不是一个 Agent 加全部工具？

我的判断标准不是 Agent 越多越好，而是领域上下文、工具权限和失败代价是否明显不同。咨询 Agent 关注检索质量和回答依据；预约 Agent 关注槽位、状态机和有副作用的操作；用户行为分析 Agent 关注跨会话事件与偏好。这三类任务的 Prompt、输入 Schema、工具权限和评测指标都不同，拆开后更容易控制上下文，也更容易定位问题。

如果把知识检索、排班、创建预约、取消预约和用户画像全部交给一个 Agent，工具集合会变大，咨询请求也可能误选写工具。我的做法是最小权限：咨询 Agent 只有只读检索能力，预约 Agent 只能提出预约相关动作，真正写入仍必须经过业务 Service 的鉴权和规则校验。这里的安全边界在代码和权限系统里，而不是只靠 Prompt。

多 Agent 的代价是额外调用、状态传递、延迟和调试复杂度，所以我没有让所有请求都走 Supervisor。明确的单意图由 Router 走快速路径，只有“先判断故障、再决定是否预约”这类任务才进行多步编排。这是在隔离性和系统成本之间做的平衡。

## 3. Router 和 Supervisor 有什么区别？你的系统属于哪一种？

Router 通常是一次分类和分发：它判断请求属于哪个类别，然后把请求交给对应处理器，本身不负责持续规划。Supervisor 是有状态的编排者：它会根据当前任务状态和前一步 Observation，动态决定接下来调用哪个专业 Agent、是否继续、澄清还是结束。

我的系统两者都用了。入口的 Router 负责快速区分咨询、预约、复合任务和未知意图，例如“E3 是什么故障”直接进入咨询 Agent，“查询我的预约”直接进入预约 Agent。“先判断是否需要上门，如果需要就约周五”会被标记为复合任务，再交给 Supervisor。

Supervisor 持有任务阶段、已完成步骤、未决问题和调用预算。它可以先拿到咨询 Agent 的诊断结果，再决定是否进入预约；如果预约信息不完整，就暂停并向用户澄清。专业 Agent 只接收完成本次任务需要的最小上下文，并返回结构化结果。因此我会把整体架构概括为：确定性路由负责快路径，Supervisor 负责复杂任务，业务工作流负责关键约束。

## 4. 请讲一条 ReAct 执行轨迹，如何避免死循环？

以“洗衣机一直排水，周六能上门吗”为例，一条可审计轨迹记录的是决策标签、Action、Observation 和状态变化，而不是模型隐藏思维链。

第一步，Supervisor 判断需要故障咨询和预约两个能力，调用 `consult_fault`，参数是设备类型和症状。Observation 返回可能原因、风险提示和证据 ID。第二步调用 `extract_booking_slots`，得到原始日期表达“周六”，同时发现缺少具体地址、联系人和期望时段。此时正确动作不是猜参数或重复调用工具，而是保存状态并提出最小澄清问题。

用户补充信息后，工作流从 Checkpoint 恢复，确定性时间服务把相对日期转成标准时间区间，再调用 `query_engineers`。服务根据技能、区域和排班返回带版本的候选方案。用户确认后，才允许提出 `create_booking`；业务 Service 会重新检查确认绑定、排班版本和幂等键，然后返回预约结果。这条决策轨迹通过结构化事件回放和定位；接入分布式追踪后，每个节点事件再关联到对应 Span。

循环控制在代码层完成：设置最大步骤数、单工具调用上限、总 Deadline、Token 或费用预算，并为每次调用生成“工具名 + 规范化参数”的指纹。如果相同调用连续出现且没有新增 Observation，就终止循环并澄清或转人工。工具超时也不会无限重试；对于有副作用的操作，要复用同一个幂等键并先查询结果，避免把一次网络超时变成两次预约。

## 5. Agent 的共享状态有哪些字段？如何避免上下文膨胀？

我先把可信运行上下文和模型可写状态分开。`tenant_id`、`user_id`、角色和权限来自认证入口；`request_id` 与 `trace_id` 标识本次请求；真正接受有副作用的业务意图时，再根据可信作用域和 `Idempotency-Key` 取得或生成持久化 `operation_id`。这些字段放在 Runtime Context 中，每次调用工具时重新注入，不能让模型修改。`session_id` 或 `thread_id` 用于定位隔离的 Checkpoint，也要和可信身份绑定。

Agent State 分三组：任务状态包含当前意图、任务阶段、已完成步骤、剩余预算和待确认动作；业务状态包含设备、故障、日期、时段、地址、候选工程师和预约状态；证据状态只保存文档 ID、摘要、工具结果引用和 Trace 关联信息。每个关键槽位还记录值、来源消息、更新时间、置信度和是否确认，方便处理继承、覆盖和追溯。

控制上下文的原则是“传结论和引用，不复制全过程”。咨询 Agent 返回诊断摘要、风险级别和来源 ID，不把全部候选 Chunk 交给预约 Agent；大工具结果存外部，State 里只放引用；每个专业 Agent 都有独立输入 Schema，Supervisor 调用前做字段投影。消息窗口按 Token 预算动态裁剪，早期对话做结构化摘要，但用户确认、地址、时间等高风险信息保留原文引用。

## 6. RAG 的数据处理流程是什么？Chunk 参数怎么定？

RAG 分离线入库和在线检索。离线阶段先解析文档并保留标题层级、页码、表格标题、产品型号、版本、生效时间、租户和 ACL，再去除页眉页脚、重复目录和乱码。切分时优先沿章节、段落和故障条目边界切，不机械按固定字符截断。

每个 Chunk 保存 `doc_id`、`chunk_id`、标题路径、型号、版本、页码、权限范围和文本哈希。文档更新时根据哈希做增量处理，旧版本失效，相关索引同步重建。在线检索前先做租户、ACL、产品和有效版本过滤，再进行关键词和向量召回，最后返回可核验的来源。

Chunk 大小没有通用最优值。故障码表适合按条目或表格行切，完整的“现象—原因—处理步骤”尽量保存在一个 Chunk 中，长段落才使用带重叠的滑动窗口。我会用标注查询集做消融，比较不同大小和重叠对 Recall@K、答案完整度、重复上下文、延迟和 Token 消耗的影响，然后按文档类型分别配置，而不是全库共用一个数字。

## 7. 为什么同时使用 BM25 和 Dense Retrieval？

因为售后知识同时包含精确标识和自然语言语义。BM25 擅长型号、故障码、零件编号和政策名称，例如 `XQG100-1436 E03`；Dense Retrieval 擅长同义表达，例如手册写“进水超时”，用户说“水一直进不来”。只用其中一路都会有明显盲区。

我先做权限、租户、产品和版本过滤，再并行运行两路召回。型号字段保留原始值，并做大小写、全半角和连字符等有规则依据的归一化，但不做可能改变型号含义的模糊改写。Dense 编码时会把标题、产品和正文一起编码，减少召回到相似症状但错误型号的文档。

两路结果通过 RRF 按排名融合，再交给 Cross-Encoder 精排。评测时会按“型号精确查询、故障码、口语症状、无答案”等类型分桶看 Recall，而不是只看一个平均数，这样才能知道混合检索到底解决了哪类问题。

## 8. RRF 如何计算？为什么不用原始分数直接加权？

RRF 只依赖各召回器给出的排名。一个文档的融合分数可以写成：

```text
RRF(d) = Σ 1 / (k + rank_i(d))
```

文档没有出现在某一路结果中，那一路就不贡献分数。比如文档 A 在 BM25 排第 1、Dense 排第 4，`k=60` 时分数是 `1/61 + 1/64`。文档 B 两路都排第 2，分数是 `1/62 + 1/62`，因此两路共同认可的 B 可能排得更靠前。

我选 RRF 的原因是 BM25 分数和向量相似度的量纲、分布都不同，直接相加必须先做稳定的分数归一化和校准。RRF 避开了这个问题，对单路异常高分也不太敏感。融合时按 `chunk_id` 去重，同一 Chunk 被两路命中时累计排名贡献，而不是复制两份。

`k` 和候选窗口仍然要验证：`k` 越大，低位结果的影响相对更高；候选窗口越大，可能提高召回，但会增加精排成本。我会在开发集上联合选择两路 Top-K、RRF 常数和精排候选数，配置冻结后再跑独立测试集。

## 9. Cross-Encoder 为什么只用于精排？失败时如何回退？

Bi-Encoder 分别编码查询和文档，文档向量可以预计算，所以适合大规模召回。Cross-Encoder 把 Query 和 Chunk 拼在一起做联合注意力，通常能更细致地判断相关性，但每个 Query-Chunk 对都要单独推理，无法经济地扫描全库。

所以我的链路是 BM25 和 Dense 先召回一批候选，RRF 融合后再让 Cross-Encoder 对有限候选打分，最后只把少量高质量证据交给生成模型。精排服务有独立超时、候选数上限和文本长度上限，避免异常长文档拖慢整条请求。

如果精排超时，但 RRF 结果有效，就回退到 RRF 排名并记录 `rerank_degraded=true`；Dense 不可用时可以退到 BM25。权限过滤、租户隔离和版本过滤不会因为降级而跳过。如果没有任何可信证据，我会明确说知识库暂时无法支持结论，而不是让模型凭常识补答案。

## 10. 怎样证明 RAG 升级后更好？

我把评测拆成检索层和答案层。检索层使用带相关 Chunk、文档版本和权限标签的查询集，比较 BM25、Dense、RRF、RRF 加精排，指标包括 Recall@K、MRR、NDCG；跨租户、错误型号和失效版本即使语义相关，也按严重错误处理。

答案层固定生成模型、Prompt 和解码参数，评估正确性、完整性、Faithfulness、引用支持度以及无答案时是否正确拒答。规则和确定性指标负责 Schema、引用存在性、工具轨迹等检查；LLM-as-Judge 用固定 Rubric 做辅助评估，并用人工标注样本校准，关键故障和政策问题仍由人工复核。

我还会做分桶和消融：按型号查询、故障码、口语描述、多轮追问和无答案分别看结果，逐项移除查询改写、混合召回或精排，定位收益来源。发布门槛同时包含质量、P95 延迟、Token 成本和降级率。这样才能得到可复现的版本对比，而不是凭几个演示问题判断效果。

## 11. 短期记忆窗口、摘要阈值和长期记忆 Top-K 怎么定？

这些参数不是拍脑袋固定，而是由任务需要和 Token 预算共同决定。简单知识问答只需要少量近期消息；预约修改和确认需要保留与槽位有关的原始轮次；早期闲聊可以摘要。我的输入预算会给系统指令、工具 Schema、检索证据和输出分别预留空间，剩余部分才用于历史消息。

参数选择用长对话回归集完成。我会改变保留轮次、摘要触发点和长期记忆 Top-K，观察槽位继承正确率、用户纠正是否生效、关键信息丢失率、噪声召回、Token 与延迟。长期记忆不是越多越好，错误或过期偏好被召回，可能比漏掉一条普通信息更危险。

运行时也会动态调整：简单请求少带历史，涉及用户纠正时回取对应原文，高风险动作执行前不只相信摘要。最终保存的是结构化事实、必要原文和可追溯引用，而不是无限增长的聊天记录。

## 12. 滚动摘要如何处理信息丢失和冲突？

我的设计不是让摘要替代原文，而是“摘要压缩背景、结构化状态保存事实、近期原文保留证据”。预约时间、地址、候选工程师和用户确认写入独立槽位，并保存来源消息 ID；摘要只负责早期对话背景和已经完成的低风险信息。

例如用户先说“周末不要安排”，后来又说“这周六可以”。我不会简单覆盖成“用户喜欢周六”，而是把长期偏好记录为避开周末，把本次会话记录为一次性例外。当前会话中的最新明确指令优先，但长期偏好仍然保留适用范围和时间。

摘要生成后要做结构校验，确认未决问题、已确认事实和禁止项仍然存在。出现冲突时，数据库业务事实优先于记忆，最新用户原文优先于旧摘要；创建预约前还会回看与本次动作绑定的确认消息。这样即使摘要有误，也不会直接改变有副作用的业务操作。

## 13. 多轮预约槽位如何继承、覆盖和解析相对时间？

每个槽位不只是一个字符串，而是包含 `value`、`source_message_id`、`updated_at`、`confidence` 和 `confirmed`。用户第一轮说“明天下午”，模型保存原始日期和时间段表达；下一轮说“还是周五上午”，这是显式修正，日期和时段被覆盖，设备、故障和地址继续继承，并保留变更关系。

相对时间由确定性时间服务解析：先把请求时间点转换到用户时区，再按当地日历解释“明天、下周五、下午”。模型只识别语言片段，代码负责转换为标准起止时间，并检查营业时间、节假日和时区。如果表达存在歧义，就把解析出的具体日期展示给用户确认。

预约状态机是 `COLLECTING → READY_TO_CONFIRM → CREATING → CREATED`。只有必要槽位齐全、候选方案有效时，才能进入待确认；确认需要绑定候选版本和规范化参数摘要。如果用户确认后又修改时间、地址或工程师，旧确认立即失效，必须重新查询候选并再次确认。Checkpoint 用于恢复流程，数据库中的预约和排班才是事实源。

## 14. 为什么选择 Qwen3-1.7B？速度测试如何保证公平？

这是一个边界清晰、输出 Schema 固定的结构化任务，不需要每次都调用大模型做开放式推理。我先用冻结评测集比较不同参数规模的候选模型，覆盖槽位抽取、缺槽判断、多轮修正、确认意图、工具选择和幻觉陷阱。选择原则是：先满足关键切片的质量门槛，再选资源占用更合适的最小模型；预约子流程因此选用 Qwen3-1.7B。

公平测试分两轨：第一轨统一硬件、推理后端、上下文、量化口径和解码参数，做严格控制变量；第二轨允许每个模型使用已冻结并验证过的推荐 Chat Template 与最优生成参数，比较它们作为完整部署方案的上限。模型预先加载并完成预热，分别记录 TTFT、端到端延迟、Decode 吞吐和峰值内存。单并发用于比较单请求延迟，多并发用于比较服务吞吐，两个口径不会混在一起。

质量也不只看 JSON 能否解析。我分别评估动作选择、关键字段、状态继承、拒绝脑补和最终协议有效性。上线门槛按关键切片的最低表现设置；如果模型版本、量化方式或运行后端改变，就重新跑完整回归，而不是沿用旧结论。

## 15. 为什么结构化任务采用 Non-Thinking 模式？

槽位抽取和动作建议属于短输出、强约束任务，我使用 Non-Thinking 模式主要为了避免额外的 Thinking 内容、减少 Token 和延迟。Qwen3 官方支持 Thinking 与 Non-Thinking 两种模式，所以我按任务路由：复杂故障分析和跨域规划使用更强的推理能力，固定 Schema 抽取优先使用 Non-Thinking。至于结构化正确率是否更高，不靠模式名称推断，而是用同一冻结集分别评测 JSON 有效率、字段准确率和动作正确率。

但关闭 Thinking 不等于只靠模型保证 JSON。推理侧仍然使用与模型版本匹配的 Chat Template 和工具调用协议，配合结构化输出约束；输出进入 Pydantic 和业务规则校验，缺槽、枚举非法、字段冲突或状态不一致时有限修复或升级处理。相对时间、排班冲突、权限和用户确认都由代码判断。

训练与推理必须使用同一套角色边界和 Tool Call 格式。SFT 的 Assistant 目标只包含约定响应，工具名和参数 Schema 统一维护，控制标记由官方模板生成，不能手写一套训练格式、推理时再换另一套解析器。

## 16. 500 条 SFT 数据够不够？

对通用能力肯定不够，但对基座模型已经具备语言能力、任务范围窄且 Schema 固定的场景，500 条高质量数据可以完成第一阶段领域适配。关键不在总数，而在是否覆盖动作、字段、状态转移和困难边界。

我先建立数据矩阵：正常抽取、缺槽澄清、多轮继承、用户修正、确认后变更、无关输入、拒绝脑补和工具参数边界都要覆盖。数据进入训练前会做 JSON 解析、枚举、时间一致性和工具参数校验，并保留来源、模板族和生成版本。

是否够用由学习曲线决定。我会用不同数据子集训练，在验证集上观察新增数据是否继续改善关键错误；冻结测试集只用于方案定型后的最终比较。若错误集中在某个切片，就围绕失败类型补充难例，而不是无差别扩大简单样本。训练、验证和测试还要按来源或模板族分组，避免同一母模板换个日期后同时出现在训练集和测试集。

## 17. SFT 和 DPO 分别解决什么问题？DPO 的 β 是什么？

SFT 先教模型“正确输出长什么样”，包括 JSON Schema、字段语义、状态继承以及什么时候输出最终回答或 Tool Call。DPO 在 SFT 模型之上学习偏好边界：两个回答格式都合法时，更偏好不脑补、先澄清、正确处理确认和权限边界的那个。

例如缺少服务地址时，Chosen 返回 `missing_slots=[service_address]`；Rejected 虽然也是合法 JSON，却编造地址并建议创建预约。这样的困难负例只在关键业务行为上不同，才能让模型学到偏好，而不是只学会区分合法 JSON 和乱码。

标准 DPO 使用 Chosen、Rejected、策略模型和参考模型的对数概率差直接构造优化目标，不需要单独训练奖励模型。`β` 控制策略相对参考模型的偏离程度；在常用 TRL 实现里，较大的 `β` 通常意味着对参考模型约束更强。它需要结合锁定版本的实现，在验证集上同时看偏好准确率、任务成功、过度拒绝和模型漂移，不能只追求训练 Loss 下降。

## 18. Response-only Loss 如何实现？为什么需要？

一条聊天训练样本包含 System、User、可能的 Tool 消息和 Assistant 输出。Response-only Loss 的含义是：所有上下文 Token 都参与前向计算，但只对目标 Assistant 响应或约定的 Tool Call 部分计算监督损失。常见实现会把不参与监督的位置标签设为 `ignore_index`，通常是 `-100`。

这样做是因为训练目标是让模型学会如何回答和调用工具，而不是学习复述用户输入。特别是在小数据、固定模板场景中，如果把 Prompt 也计入 Loss，大量梯度会浪费在预测重复模板上，削弱对关键 JSON 字段和动作边界的学习。

实现时我不会按字符串查找“assistant”后粗暴截断，而是用与 Qwen 推理一致的 Chat Template 生成 Token 和角色边界，再构造 Loss Mask。训练前会抽样打印 Token、角色、标签掩码和有效监督 Token 数，并覆盖多轮对话、Tool Call 和 Tool Result，防止模板升级后把全部标签屏蔽，或者误把用户内容算进 Loss。

## 19. 如何检查训练集是否污染冻结评估集？

我的污染控制分三层。第一层是数据血缘隔离：冻结集先建立并设为只读，训练数据生成流程不能读取测试答案；每条数据保留来源、模板族、生成器版本和父样本关系。第二层是文本去重：对规范化后的输入、上下文和目标做精确哈希与近似字符串匹配。第三层是语义和模板检查：用 Embedding 近邻、槽位组合与模板 ID 查找“只换了日期或姓名”的变体。

数据切分按来源实体或模板族做 group split，而不是简单随机切行。同一业务类别可以在训练和测试中都出现，例如都包含“确认后修改时间”，否则无法评估同类泛化；但不能由同一个母模板改写出来。

最终污染报告至少包含精确重复、近似重复、跨集合模板族和高相似近邻的统计，并对临界样本人工复核。验收口径是：所有命中的同源或近重复样本完成剔除，冻结集在训练期间保持只读，最终报告能够追溯每条排除记录。

## 20. 如果删除大模型，只用规则和小模型，业务还能完成吗？

核心预约闭环可以完成，而且我本来就把关键业务约束放在确定性代码里。预约状态机、权限、时间换算后的规则校验、工程师筛选、排班冲突、幂等和事务都不依赖大模型；高频槽位抽取也可以由规则或本地小模型完成。

大模型的价值主要体现在开放式故障描述理解、基于证据的自然语言回答、跨领域任务规划和自然澄清。用户描述越口语化、任务组合越多，纯规则的覆盖成本越高。反过来，如果业务只有少量固定意图和明确流程，我会优先选择状态机加分类器，不会为了使用 Agent 而使用 Agent。

所以我的架构原则是分层：模型负责理解和建议，Workflow 负责流程，Service 负责权限与业务规则，数据库负责最终事实。安全关键路径可以在模型不可用时降级为规则流程；开放式咨询能力则明确降级或转人工。这种设计既利用模型的语言能力，也不会把系统可靠性寄托在模型的自由发挥上。
