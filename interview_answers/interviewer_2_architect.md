# 系统架构师面试官：18 道高频架构题可直接口述版

> 使用方式：每题先说结论，再讲关键链路和取舍，最后用一句话收口。正文按 1—3 分钟口述长度整理。

## 1. 请画出系统架构图，并说明一次请求的完整调用关系

我把系统分成接入层、编排层、领域服务层和数据基础设施层。用户请求先进入 FastAPI，完成认证、租户识别、Schema 校验、限流，并建立 `trace_id`、`session_id` 和幂等上下文。确定性 Router 识别咨询、预约或复合任务：简单请求直达专业 Agent，只有跨领域、多步骤任务才交给 Supervisor。

咨询链路是“查询改写 → ACL 与元数据过滤 → BM25/Dense 并行召回 → RRF 融合 → Cross-Encoder 精排 → 大模型基于证据生成”；预约链路由本地小模型提取槽位，但日期计算、权限判断和创建预约都由确定性代码负责。槽位完整后先查询工程师与排班，向用户展示带版本的候选方案；用户明确确认后，Booking Service 再校验身份、候选版本、幂等键和最新时段，在同一事务写入 Booking、幂等结果和 Outbox。通知由 Worker 异步投递，失败不回滚预约。

这套架构的核心原则是：模型负责理解和建议，Service 决定能否执行，数据库保存最终事实。

**高频追问：为什么不让一个大模型包办？** 因为路由、权限、确认、幂等和事务都有明确规则，用确定性代码更低成本、更易测试；模型只放在语言歧义和开放式推理真正产生价值的位置。

## 2. 为什么采用分层架构，而不是把逻辑都写在 Agent 里？

我分层的目的不是追求目录整齐，而是隔离变化和建立信任边界。API 层处理 HTTP 契约和可信身份；Agent 层处理语言理解与任务编排；Service 层保存确定性业务规则；Repository/Infrastructure 层适配数据库、检索、模型和消息设施。

最重要的一条约束是 Agent 不直接拼 SQL，也不直接修改预约表。它只能提出类似 `create_booking(command)` 的结构化建议，Service 从服务端 ActorContext 取用户与租户身份，再校验动作 Schema、授权、确认令牌、幂等和数据库事实。这样即使 Prompt 被注入或模型输出异常，也越不过业务门禁。

分层还降低替换成本：SQLite 迁移 PostgreSQL 主要改变仓储和事务实现；Qwen 换成另一种本地模型主要改变 Model Adapter；RAG 从进程内模块变成独立服务时，Agent 依赖的仍是一份稳定的检索契约。早期可以同进程部署这些逻辑层，出现独立扩容或组织边界后再物理拆分，避免一开始就承担微服务通信和运维成本。

## 3. 为什么把 RAG 设计成独立 MCP Server？

我把 RAG 设计成独立 MCP Server，因为检索不仅服务咨询 Agent，还要承载统一的摄取、版本、ACL 过滤、混合检索、精排、引用和评测。它有独立的索引生命周期和计算资源，拆开后可以独立发布、扩容，也能让多个 Agent 复用同一份检索契约。

选择 MCP 的价值在于标准化能力发现、输入 Schema 和工具调用。咨询 Agent 可以发现 `search`，管理端可以使用 `ingest`、`delete_version` 等能力，调用方不必绑定具体检索实现。但 MCP 是协议边界，不等同于完整的安全与高可用方案。我仍会在传输层做服务身份和加密，在 RAG 服务端按可信用户委托上下文强制注入 tenant/ACL 过滤，并将只读查询与管理写操作分开授权和审计，绝不相信模型参数里自报的 `tenant_id`。

独立部署也有代价：多一次网络跳转、版本兼容和故障面。因此实现上仍保留稳定的端口适配层，本地开发可以连接轻量实现，部署环境连接独立 MCP Server；这样不会把协议选择扩散到业务代码。

**高频追问：RAG 服务宕机如何降级？** 精排失败可在服务内部退回 RRF，Dense 失败可退回 BM25；整个服务不可达时必须切到真实存在的备用检索通道，否则明确提示暂时不可检索或转人工。

## 4. 系统状态由谁管理？什么是 Source of Truth？

我把状态分成三类。第一类是身份与权限，来源是经过验证的认证声明和授权策略；第二类是预约、排班、幂等结果等业务事实，数据库是唯一事实源；第三类是 Agent 工作状态，例如当前阶段、已收集槽位、候选方案和待确认动作，由 Checkpointer 管理。单机运行可以使用进程内实现；多实例部署时换成共享的持久化实现，状态模型和线程隔离键保持不变。

Checkpoint 用于恢复流程，不代替数据库事务。比如 Agent 状态里保存过“工程师明天下午可用”，真正创建时仍要重新查询并依靠数据库约束防冲突。工具成功后，我把数据库返回的 `booking_id` 和状态写回工作流，而不是把模型生成的文本当成功结果。

会话按 `tenant_id + user_id + session_id` 隔离。槽位还会保存来源消息和更新时间，用户后续说“改到周五上午”时，只覆盖相关字段并让旧候选与旧确认失效。跨线程的长期偏好放 Store，线程内恢复信息放 Checkpointer，二者都不能覆盖用户最新明确指令或数据库事实。

## 5. 两个用户同时预约同一工程师、同一时间段，怎么处理？

我把它当数据库不变量，而不是先查后写的业务判断。两个请求可能同时查到空闲，所以应用层检查只能改善体验，最终必须由同一事务和数据库约束兜底。

创建流程是：先根据稳定的 `Idempotency-Key` 查幂等记录；首次请求进入短事务，再读取最新排班并写预约。SQLite 闭环使用 `BEGIN IMMEDIATE` 串行化短写事务，并在锁内复查时段；多实例版本迁移 PostgreSQL 后，使用 `tenant_id + engineer_id + tstzrange` 的 GiST 排斥约束阻止有效预约区间重叠。约束冲突统一映射为业务冲突，重新查询候选并要求用户再次确认。

幂等和并发冲突要分开：幂等解决“同一个意图因重试被执行多次”，排斥约束解决“不同用户竞争同一资源”。同一个幂等键配相同请求摘要时返回原结果；配不同摘要时直接拒绝，避免旧 Key 被复用到另一笔业务。

**高频追问：加 Redis 分布式锁行不行？** 可以用于削峰或减少热点冲突，但锁过期、网络分区和进程暂停都会带来边界情况，所以数据库约束仍是最后防线。

## 6. 预约是时间区间，唯一索引为什么不够？如何防重叠？

唯一索引只能阻止完全相同的值，识别不了 `14:00—16:00` 与 `15:00—17:00` 的重叠。我统一使用带时区时间，并采用左闭右开 `[start_at, end_at)`，因此前一单 16:00 结束、后一单 16:00 开始不会冲突，同时增加 `CHECK (start_at < end_at)` 拒绝空区间和反向区间。

迁移 PostgreSQL 后，我会用 `tstzrange(start_at, end_at, '[)')` 表示占用区间，并通过 `EXCLUDE USING gist` 组合租户、工程师等值比较和时间范围的 `&&` 重叠运算。标量列由 `btree_gist` 提供对应 GiST 操作类。取消预约后允许释放时段时，约束只覆盖明确的占用状态，例如 `CONFIRMED`、`IN_SERVICE`；另一种做法是将有效资源占用单独建表，在状态转换事务中维护，语义更清晰。

SQLite 阶段则用 `BEGIN IMMEDIATE` 获取写事务，在事务内执行 `old.start < new.end AND old.end > new.start` 检查并插入。这个方案适合单机和低写并发；进入多实例和高并发后，我会迁移到 PostgreSQL，让范围约束承担最终一致性。

## 7. 预约成功，但确认消息发送失败，怎么办？

预约是核心事实，通知是派生动作。我用 Transactional Outbox 消除数据库写入和外部消息发送之间的双写窗口：在一个数据库事务中写 Booking、幂等终态和 `BOOKING_CREATED` Outbox 事件。事务提交后，Worker 认领 Outbox 并投递；通知失败只进入重试和告警，不回滚已经占用的预约。

Worker 使用行锁或租约认领任务，失败按总时间预算做指数退避和 Jitter，达到上限后进入死信或人工处理。由于“消息发出后、Outbox 标记成功前”可能崩溃，系统采用至少一次投递，消费者必须按稳定 `event_id` 幂等。消费侧在本地事务写 Inbox 和待发送 Delivery，再调用短信供应商；供应商支持幂等键时继续传同一个 `event_id`。

如果外部供应商超时且无法查询状态，就会出现发送结果未知。此时不存在魔法般的端到端 Exactly Once，我会按业务风险选择“允许极少量重复但避免漏发”或“避免重复但可能漏发”，并通过对账和人工补偿缩小影响。

## 8. 为什么项目早期使用 SQLite？它的边界是什么？

我在早期选 SQLite，是因为它部署成本低、事务语义完整，能够快速把预约、幂等和 Outbox 放到同一个可运行闭环里。它非常适合单机开发、原型验证和低写入压力场景。

我也明确利用它的边界来决定迁移时机。WAL 让读写可以并行，但同一时刻仍只有一个写者；长写事务、后台任务与 API 同时写入时会形成锁等待。因此事务必须短，模型调用和网络请求一律放在事务之外，并监控 `SQLITE_BUSY`、写锁等待和事务时长。

当业务进入多实例部署、写并发上升，或需要范围排斥约束、连接池和更细粒度锁时，我会迁移 PostgreSQL。迁移前先冻结 Repository 契约和时区语义，再做双写校验或离线数据校验，最后切流。Redis只用于缓存、限流或协调，不替代预约数据库的唯一与排斥约束。

## 9. 系统如何横向扩容？

横向扩容的第一步不是多开几个 FastAPI 实例，而是先消除进程内唯一状态。业务事实、幂等结果和 Checkpoint 放到可共享的持久存储；数据库唯一/排斥约束保证正确性；线程级并发更新使用 CAS 或带版本更新，Redis 可承担限流和短期协调，但不承担最终事实。

API 层做成无状态后可以直接水平扩展。Outbox Worker 使用 `FOR UPDATE SKIP LOCKED` 或租约并行认领，每条任务携带稳定幂等 ID。检索服务按不可变 `index_version` 构建和发布：实例先加载、校验新版本，再原子切换流量并保留旧版本直到在途请求结束。模型服务独立设置并发上限、有界队列和背压，避免推理占满 API 事件循环。

我会按饱和点扩容，而不是按组件名平均加机器：API 看 CPU 和连接，数据库看锁等待和连接池，检索看 QPS 与尾延迟，模型看队列等待、显存和 Token 吞吐，Worker 看最老 Outbox 年龄。哪一层先达到容量阈值，就优先扩该层或做削峰。

## 10. 本地小模型和远端大模型如何路由？

我的原则是“任务路由在前，模型路由在后”。顶层咨询、预约、复合意图优先由规则或轻量分类器完成；固定 Schema 的槽位抽取、字段修正和确认语句识别交给本地小模型；开放式故障解释、复杂语言和跨领域规划再使用远端强模型。

本地模型输出必须经过 JSON/Pydantic、枚举、时间和状态机校验。模型输出 `TOOL_CALL` 也只是一条建议，用户确认由服务端状态机绑定候选版本与参数摘要。Schema 失败时，在剩余 Deadline 内做一次受控修复；仍失败或关键字段歧义时升级远端结构化模型。路由依据来自离线评测集和运行时信号，而不是模型自报的置信度。

这套分流同时控制成本、延迟和隐私：高频结构化任务尽量本地完成，复杂低频任务购买更强能力。无论切到哪种模型，认证、租户、确认、幂等和事务门禁始终是同一套，模型降级不会改变权限。

**高频追问：为什么不用本地模型做所有任务？** 模型选择看任务质量门禁和资源曲线。小模型在固定域结构化输出上性价比高，但开放式推理与长上下文往往需要更强模型；强行统一反而让质量或成本失控。

## 11. 如何设计端到端超时预算？

我从用户体验 SLO 倒推一个绝对 Deadline，并把“剩余时间”传到每个下游，而不是让每个组件都拿一份完整总超时。路由和状态读取预算较小，检索与精排分别限时，生成占主要预算；数据库写事务必须短，而且不包含模型和网络调用。队列等待也计入总预算。

重试共享同一 Deadline，并且只重试明确的瞬时错误。Cross-Encoder 接近超时时直接使用 RRF 结果；远端模型剩余时间不足时不再发起新调用；数据库锁冲突只做有限退避。指数退避配合 Jitter 和最大次数，避免依赖恢复时所有客户端同步重试形成流量尖峰。

副作用请求还要区分“调用超时”和“执行失败”。客户端取消等待并不代表数据库事务被撤销；预约响应丢失时，我先按原幂等键查询结果，状态未知就返回可查询的操作 ID，而不是再次创建。预算值通过压测、依赖延迟分布和业务 SLO 校准，重点观察 P50/P95/P99、排队时间和各阶段预算耗尽原因。

## 12. 各组件失败时如何降级？

我的降级原则是只降低质量或功能，不放宽数据范围、工具权限和副作用门禁。

| 故障 | 处理方式 |
|---|---|
| Cross-Encoder 失败 | 使用 RRF 排名并记录 `degraded_reason` |
| Dense 失败 | 回退 BM25-only，保留引用 |
| RAG 整体不可用 | 切真实备用检索；否则提示暂不可检索或转人工 |
| 远端模型限流/超时 | 返回证据摘要、稍后重试或转人工 |
| 本地模型 Schema 错误 | 一次受控修复，仍失败则升级模型或定向澄清 |
| 数据库不可用 | 写请求快速失败或返回已持久化操作 ID，拒绝以内存结果冒充成功 |
| 预约结果未知 | 按原幂等键对账 |
| 通知失败或重复 | Outbox 重试，Inbox 与业务键去重 |

每条降级路径都预先编码并受 Deadline 限制，同时记录原因、持续时间和业务影响。恢复时先健康探测，再小流量回切，防止依赖刚恢复就被积压请求再次打垮。对于预约等写操作，宁可明确不可用，也不绕过确认、授权和数据库约束。

## 13. 哪些内容适合缓存？如何保证权限与新鲜度？

我先按“可复用性、变化速度、敏感度和事实地位”分类。文档 Embedding 可按 `content_hash + preprocessing_version + embedding_version` 缓存；检索结果键包含租户、ACL/角色版本、索引版本、规范化 Query 和过滤条件；答案缓存还要绑定 Prompt、模型、知识版本和引用。

工程师排班变化快，只做很短 TTL 或不缓存，创建预约前必须回源数据库。用户偏好缓存按 `tenant_id + user_id` 隔离，更新后主动失效。权限判断既不能跨用户共享，也不能因为缓存命中而跳过授权；Query 可能包含地址和电话，所以敏感内容采用最短必要保留、加密和访问审计，标准 FAQ 才适合较长缓存。

失效优先用不可变版本和领域事件：新 `index_version` 发布后，新请求自然使用新键；预约事务提交产生事件，使相关工程师和日期的可用性缓存失效。为防击穿，我会用请求合并、随机 TTL 和限速。缓存永远是性能层，不是预约、排班或权限的事实源。

## 14. Prompt、模型、Schema 和索引如何版本化？

我把一次可发布的 AI 能力定义成不可变 Manifest。生成侧固定 `prompt_version`、模型或 Adapter、Tokenizer、Chat Template、生成参数和输出 Schema；检索侧固定 Embedding、切分与清洗规则、文档快照和 `index_version`。Embedding 或预处理变化时构建新索引，评测通过后原子切换，避免同一索引混入不同向量空间。

工具协议使用显式 `tool_schema_version` 和契约测试。新增可选字段是否兼容，要看旧消费者是否允许未知字段以及默认语义是否变化；字段重命名、类型改变或语义改变直接升不兼容版本，并设置双读或适配窗口。灰度与回滚以完整 Manifest 为单位，避免只回滚模型却继续使用不匹配的 Prompt 或索引。

复现实验时记录输入摘要、Manifest、检索证据 ID、依赖版本和运行参数。远端模型可能滚动升级且采样具有随机性，所以这里追求的是“可解释地复现上下文和比较结果”，而不是承诺逐 Token 完全一致。

## 15. Agent 系统如何做可观测性？

我的可观测模型以入口请求为根 Trace，在 Router、Supervisor step、专业 Agent、模型调用、BM25/Dense/Rerank、工具调用和数据库事务建立父子 Span；异步 Outbox 用 Span Link 或传播上下文连接生产者与消费者。先用统一关联 ID 和结构化事件保证单进程链路可回放，跨服务部署时再由 OpenTelemetry 导出完整 Trace。模型记录版本、耗时、Token 和结束原因；RAG 记录索引版本、候选 ID、排名变化和降级原因；工具记录参数摘要、结果码与幂等状态。Prompt、文档正文、电话和地址默认不进入普通日志。

指标从四个黄金信号展开：延迟、流量、错误和饱和度，再补模型 TTFT、Token 用量、检索 Recall 代理指标、工具成功率、数据库锁等待、队列等待、Outbox 最老积压与降级率。`user_id`、`request_id`、`chunk_id` 这类高基数字段放 Trace 或受控日志，不作为 Metrics 标签。

审计日志与可观测日志分开。写操作审计记录可信 actor、动作、资源、确认与参数摘要、决策结果、时间和关联 Trace，并设置独立访问控制与保留策略。Trace ID 用于关联，Idempotency-Key 用于副作用去重，两者职责不同。

## 16. 如何定义发布门禁？

我把门禁分为四层。第一层是确定性不变量：跨租户访问、未确认写入、重复预约、Schema 破坏等关键安全切片零容忍，并通过单元、契约和数据库集成测试验证。第二层是模型与 RAG 质量：结构化输出看 JSON 解析率、Schema 遵循、字段 Exact Match 和动作正确性；RAG 看 Recall@K、MRR/NDCG、引用支持度和无答案拒答。

第三层是性能与成本：比较 P95/P99、TTFT、队列等待、吞吐、Token 和资源占用。第四层是韧性：覆盖依赖超时、响应丢失、数据库冲突、重复投递、Worker 崩溃与恢复对账。阈值来自上一稳定版本、业务最低要求和关键切片，不用一个平均分掩盖高风险退化。

我把发布流程定义为“开发回归集 → 冻结评测集 → 小流量灰度 → 在线业务指标 → 自动或人工回滚”。评测集按设备、故障类型、语言表达、缺槽、多轮修改和越权攻击分层，避免测试泄漏。每次结果绑定版本 Manifest，使问题可以定位到 Prompt、模型、Schema 或索引中的具体变化。

## 17. 如果要求两周上线 MVP，你会砍掉什么？

我会保住完整业务闭环和安全不变量，砍掉不直接改善首版成功率的复杂性。首版保留认证与租户隔离、确定性 Router、可引用的检索基线、预约槽位状态机、工程师候选查询、明确确认、幂等事务、冲突约束、最小 Outbox 和结构化日志。复合任务先用确定性 Workflow 编排，路径清晰、容易测试。

咨询检索先做“租户/产品/版本过滤 + BM25 + `chunk_id` 引用”，因为故障码、型号和部件名适合精确检索。自然语言症状集证明稀疏召回不足后，再增加 Dense、RRF 和 Cross-Encoder。本地小模型如果结构化门禁不稳定，首版可用规则、表单和远端结构化模型组合，业务不被单一模型阻塞。

复杂长期记忆、用户行为分析 Agent、DPO、MCP 物理拆分和高度自主的多 Agent 循环后置。每个新增模块都要由真实失败样本证明价值，并回答三个问题：改善哪个指标、增加什么故障面、如何回滚。两周 MVP 的目标不是功能列表最长，而是闭环可用、写操作可信、问题可定位。

## 18. 业务量增长 100 倍，最先崩在哪里？怎么演进？

我不会凭经验直接断言某个组件必然最先崩，而是先画容量模型并做分阶段压测。高风险点通常包括数据库写锁与连接池、本地模型排队、Cross-Encoder 计算、远端模型配额、Outbox 积压，以及本地索引在多实例间的版本一致性。真正的瓶颈顺序取决于咨询/预约比例、上下文长度、写入峰值和依赖配额。

压测时我把总延迟拆成接入排队、连接池等待、数据库锁、检索、重排、模型 TTFT/生成和外部限流，并观察吞吐继续上升时哪项饱和。先保证正确性：共享持久状态、数据库最终约束和幂等；再迁移 PostgreSQL 与可恢复 Worker；随后将模型和重排独立成有界服务，加入背压与配额；最后按热点增加缓存、索引分片或副本。

扩容不只看均值。我重点关注 P95/P99、拒绝率、队列长度、最老任务年龄和错误预算。达到预设饱和阈值时，优先限流、减少非关键精排或转异步，保护预约事务等核心路径。每一次扩容后重新压测，确认瓶颈确实转移，而不是被监控盲区掩盖。
